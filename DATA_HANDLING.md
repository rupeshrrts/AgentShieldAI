# AgentShield — Data Handling

Answers to the standard data-protection questions, verified against the code at version 2.1.0 ("SaaS phase 1": self-serve companies, trials and licences; "SaaS phase 2": Razorpay payments; 1.5.1: sign-up without email confirmation; 2.0.0: separate internal admin console for AgentShieldAI staff, with staff roles and mandatory MFA; 2.1.0: Individual accounts, email confirmation before the trial, usage metering, prepaid credits, personal API tokens; 2.5.0: optional Network Agent, a local proxy that decrypts only the AI domains and reuses the shared detector/evaluator — see §2). Items that depend on how you deploy (and therefore cannot be verified from the code) are marked **[deployment]**.

## 1. What data is collected from browser activity?

| Data | When | Leaves the browser? |
| :--- | :--- | :--- |
| Prompt text on supported AI sites | When the employee sends a prompt | Only as described in §5 |
| Names and sizes of files attached on AI sites | On upload | Yes, in the event (if "store text of prompts that broke a rule" is on) |
| Content of text files (≤ 2 MB) attached on AI sites | On upload, read in memory | **Never** |
| Hostname of each page opened | On navigation, compared with block lists | Only for sites blocked by the account's own BLOCK list or as an unapproved AI tool (as a `dlp.*` event) |
| Website category of a blocked page | The browser compares every page with the category lists built into the extension (`rulesets/`, generated from the HaGeZi DNS blocklists plus AgentShield's own additions in `web-category-additions.json`); no lookup service is called | Only the category of a page blocked by category blocking (`dlp.category.<id>` event, e.g. "adult website"); **the hostname is not sent** |
| Employee ID | The email of the account that activated the browser. The server sets it from the authenticated device on every event and heartbeat; the extension does not choose it and does not read the Chrome profile email (it no longer requests the `chrome.identity` permission) | Yes, on every event and heartbeat |
| Browser metadata | At activation, and each sync (~5 min) | Yes: device ID, browser name/version, OS platform, extension version, policy version |
| Activation code | Once, at activation | Only the single-use activation code goes to the AgentShield server; the extension never asks for an email or password, and the code is not stored in the browser |
| Device public key | Once, at activation | Yes, the public half of the browser's key pair. The private key never leaves the browser |
| Event ID (`client_event_id`, 2.1) | With every event | Yes: a random ID per event, so the server stores and counts each event once (no personal data) |

Every event an activated browser reports for an inspected prompt is also **counted** as one prompt check for usage and billing (2.1): the server keeps per-day counts per account and person (`usage_daily`), not extra content.

Browsing history is **not** collected. Prompt checks run only on the supported AI sites (`extension/src/content/adapters/chatgpt.ts`).

## 2. What is inspected locally?

All prompt text and text-file content is inspected inside the browser by `extension/src/content/detector.ts` and decided by `extension/src/shared/policy.ts`. No content is sent anywhere to make a decision.

**With the Network Agent (2.5):** on a PC running the optional Network Agent (`agent/`), inspection happens locally in the agent process instead of the page. The agent decrypts **only the AI domains** listed in `agent/agentshield_agent/config.py`; all other HTTPS (banking, health, mail, everything else) is tunnelled without being decrypted or read. For an AI request it extracts the prompt text and runs the **same** detector and policy evaluator as the backend (`backend/app/detection/detector.py`, `backend/app/policies/evaluator.py`), so no prompt content is sent anywhere to make a decision. What then leaves the PC is only the event described in §5 (prompt text masked by the same rules, and only if the account stores it); a redacted prompt is rewritten in the request before it reaches the AI site. File uploads and binary bodies are not read.

## 3. What is stored, and where?

**In the browser:**
* `chrome.storage.local` (inside the Chrome profile on disk, not encrypted by AgentShield): a non-secret activation record (server address, device ID, account email, organization name), rules, keywords, settings, website lists, a random install ID, last known employee status, and a queue of up to 500 unsent events (masked as in §5). No password, activation code or device key is stored.
* IndexedDB: the browser's ECDSA P-256 key pair, created with WebCrypto as **non-extractable** (the private key cannot be read out or copied by scripts, other extensions or a copy of the storage).
* Memory and `chrome.storage.session` only: the current 15-minute session token and the server's licence verdict that came with it (plan, state, end date; shown in the popup), cleared when the browser closes. Access never depends on licence flags stored in the browser: only a fresh server session grants it.
* Extension 1.9.0 (2.6) talks to no program on the computer (no native messaging) and stores nothing new. Besides the rule sync it asks the server once a minute for one number, the organization's rule revision (`GET /api/v1/policies/revision`); that request carries only the device session and sends no browsing or prompt data. The `pcAutoConnectPaused` flag of extension 1.8.0 is no longer used.

**On a Windows PC where the older AgentShield Windows app (2.4) was installed** (the extension no longer uses it since 1.9.0):
* `%LOCALAPPDATA%\AgentShield\pc-connection.json` (per Windows user): server address, PC ID, account email, account name, the key's name and the connection time. No password, activation code or token.
* The PC's ECDSA P-256 key in that Windows user's CNG key store (Microsoft Software Key Storage Provider), created with export disabled. Only its public key is sent to the server.
* `%LOCALAPPDATA%\AgentShield\app.log`: connection events and errors (no codes or tokens), at most 256 KB.
* Machine-wide (installer, `HKLM\SOFTWARE\AgentShield`): server and portal addresses, extension IDs, install time; the native messaging manifest `com.agentshield.helper.json` next to the app. The app sends the server the Windows computer name and "Windows 10/11" so the portal can list the PC, and, for each browser code, the browser's name and version.

**On the server** (database tables, `backend/app/db/models.py`):

| Table | Contents |
| :--- | :--- |
| `computers` (2.4) | PCs connected through the Windows app: account, Windows computer name, "Windows 10/11", public key, status, connected / last seen / removed times. `devices.computer_id` links its browsers; `activation_tokens.computer_id` marks codes the PC made (hashes only) |
| `security_events` | Time, employee ID, site, application, rule, category, severity, action, outcome, extension/policy version, employee's stated reason, the extension's random event ID (`client_event_id`), and prompt text **only as allowed by settings and always masked** |
| `usage_daily` (2.1) | Per account, person (account email) and UTC day: number of prompt checks, how many were paid with credits, and how many were blocked, warned and redacted. Counts only, no content |
| `credit_ledger` (2.1) | Every change of an account's prepaid credit balance except per-check spending: amount, kind (purchase, refund, dispute, dispute_won, grant, adjust, referral (2.3)), reference (Razorpay payment ID, `staff:<email>` or `referral:<id prefix>`), note or reason, balance after, who, when |

| `users` | Customer accounts (ADMIN, VIEWER, EMPLOYEE; the former SUPERADMIN role is converted to ADMIN at startup): email, optional display name (2.1), role, enabled/disabled, email-verified time (set by opening the sign-up confirmation link, accepting an invite or using a password-reset link; required only to claim the free trial), password as a PBKDF2-HMAC-SHA256 hash (600,000 iterations for new hashes), and a session version number (raised to sign out all sessions) |
| `user_invites` | Invited email, role, SHA-256 of the invite token, expiry, accepted/revoked times, who created it |
| `staff_users` | AgentShieldAI internal staff (separate from customer accounts): email, name, staff role, enabled/disabled, password hash (PBKDF2-HMAC-SHA256), authenticator secret **encrypted** with Fernet (key `STAFF_MFA_KEY`, or derived from `SECRET_KEY`; rotating `SECRET_KEY` without a `STAFF_MFA_KEY` makes the stored secrets unreadable, so authenticator codes stop working until an owner resets them), MFA enrolment time, last accepted code step (prevents reuse), must-change-password flag, session version, last sign-in time, who created it |
| `staff_recovery_codes` | Staff member, recovery code stored only as a **SHA-256 digest** bound to that staff account (the digest covers the staff ID and the code; the codes are random, so a fast digest suffices; not a password hash), used time (each code works once) |
| `staff_invites` | Staff member, SHA-256 of the invite token (`ast_…`, 48 hours, single use), expiry, accepted/revoked times, who created it |
| `email_verifications` | Emailed links (purpose: sign-up confirmation or password reset): account, SHA-256 of the link token, expiry, used time |
| `plans` | The plan catalogue set by the platform owner in the internal console: name, length, browser limit, price, currency, features, availability, included prompt checks per month (2.1; also the Free plan's monthly checks, 2.3), prompt checks per credit pack (2.1); for the monthly plan also the Razorpay plan ID and the price it was created with |
| `licenses` | Per company: plan, kind, status, start and end dates, browser limit, `payment_ref` (for trial licences granted by staff: `manual:<staff email>`; for PAID or INTERNAL licences granted by the platform owner without a verified payment: `exception:<staff email>`; for bought plans: the Razorpay payment ID; licences granted before 2.0 keep `manual:<admin email>`), who created it, revoked time, by whom and why |
| `billing_orders` | Purchase attempts per company: the admin's account ID, plan, one-time or subscription, amount and currency, Razorpay order or subscription ID, status (created / paid / failed / refunded / partially refunded), failure reason, receipt number, created and paid times |
| `billing_payments` | Payments Razorpay confirmed as captured: company, order, Razorpay payment ID (unique), amount, currency, payment method as reported by Razorpay (e.g. `card`, `upi`), status (captured / refunded / partially refunded / disputed), refunded amount, the licence it created, receipt number, time |
| `billing_subscriptions` | Monthly subscriptions: company, plan, Razorpay subscription ID, status, whether renewal is cancelled, current period end |
| `webhook_events` | Every Razorpay webhook received: Razorpay event ID, event name, processing status (received / processed / ignored / failed), error message (up to 500 characters), received and processed times. The webhook body itself is not stored |
| `license_adjustments` | History of manual licence changes such as extensions: old and new end date, who, when, and the stated reason (e.g. an invoice number) |
| `trial_claims` | One row per free trial: company, account ID, licence, **normalized** email (lower-case; Gmail dots and `+tags` removed), email domain, a **keyed SHA-256 hash of the claimant's IP address** (the raw IP is not stored here), time. Used to refuse repeat trials |
| `notifications` | Plan reminders per company (7, 3, 1 days before the end and at the end; for individual accounts the end notice says the account moved to the Free plan), credit notices and referral bonus notices (2.3): the licence (if any), notice kind, title and text, whether it was emailed, created and read times |
| `extension_releases` | Published extension versions: version, notes, SHA-256, minimum Chrome/Edge version, which is current |
| `activation_tokens` | Account, SHA-256 of the activation code plus its first 10 characters (to identify it), expiry, used/revoked times |
| `devices` | Account, the browser's public key, browser name, OS platform, status (Pending/Active/Revoked), created and last-seen times, who approved it, revoked time and by whom |
| `device_keys` | Retired pre-1.3 device keys (SHA-256 hashes only); not accepted unless `LEGACY_DEVICE_KEYS_ENABLED=true` |

| `policies`, `domain_rules`, `restricted_keywords`, `organization_settings`, `organizations` | Configuration; `organizations` also holds the account name (individual accounts: the person's name or the part of the email before the @; company workspaces: the company name), the account type (INDIVIDUAL or COMPANY), the prepaid credit balance, the account's own monthly prompt-check limit, a random referral code for its invite link (2.3, created the first time the invite card is opened) and, if AgentShieldAI staff suspended it, the suspension time and reason |

No plaintext invite token (customer or staff), confirmation-link token, password-reset token, activation code, personal API token, recovery code or password is stored; staff authenticator secrets are stored only encrypted. The temporary password printed by `python -m app.cli create-platform-owner` is shown once and stored only as a hash. Staff invite links (`#staff-invite=ast_…`) also carry the token in the URL fragment; in development without SMTP they are written to the server log. Activation codes and personal API tokens are shown once in the dashboard; sign-up confirmation, invite and password-reset links are sent once by email (in development without email, printed to the server log). Links carry the token in the URL fragment (`#verify=…`, `#invite=…`, `#reset=…`), which browsers do not send to servers, so it does not appear in web-server access logs. Self-registered accounts are signed in before their email is confirmed; opening the confirmation link (or a password-reset link) marks the email as verified, which is required only to claim the free trial.

**Payments:** AgentShield handles **no payment card or UPI data**. Plans and credit packs are bought through Razorpay's hosted Checkout, so card, UPI and bank details are entered on Razorpay's page and go straight to Razorpay; the AgentShield server stores only Razorpay's IDs, amounts, the payment method name, statuses and receipt numbers (tables above). The platform owner can still grant paid plans manually in the internal console as an audited exception (with a reason such as an invoice reference). Payment receipts are generated on request from these rows and are not stored as files.

## 4. Which backend APIs or third-party services receive data?

* **Extension:** only the AgentShield server set by IT policy (`apiUrl`) or, if none, the one named in the activation code. No analytics, no third parties.
* **Server:** its database and, when configured, your SMTP server (`SMTP_HOST`), which receives sign-up confirmation, invite, staff-invite, password-reset and plan-reminder emails (recipient address, the link or reminder text). It also contacts **Razorpay** (payment processor, `RAZORPAY_API_BASE`), but only when `RAZORPAY_KEY_ID` and `RAZORPAY_KEY_SECRET` are configured: to create orders, monthly plans and subscriptions (amount, currency, plan name, and notes with the company ID, plan code, AgentShield order ID and the buying admin's email), fetch and capture payments, cancel subscriptions and request refunds (amount, the staff member's reason and email). Razorpay sends signed webhooks back about payments, refunds, disputes and subscriptions. It calls no other external services.
* **Razorpay Checkout (admin's browser):** when a company admin clicks Buy/Subscribe, the dashboard loads `https://checkout.razorpay.com/v1/checkout.js`, which receives the public key ID, the order/subscription ID, the plan description and amount, and the admin's email as prefill; the admin then enters payment details directly with Razorpay. Razorpay processes them under its own terms; for subscriptions Razorpay may also notify the customer itself.
* **Dashboard:** the AgentShield API, plus **Google Fonts** (`dashboard/index.html`), which means each admin's browser contacts Google when the dashboard loads. Self-host the fonts if this is not acceptable.
* **Internal admin console (staff browsers):** the AgentShield API (`/internal/*` only) and Google Fonts (`admin-console/index.html`). The authenticator QR code is drawn in the browser (`qrcode` library); the MFA secret is not sent to any third party. The staff session token is kept in `sessionStorage` and cleared when the tab closes.
* **Hosting providers [deployment]:** your database host (e.g. Supabase) and server host process the stored data.

## 5. Is sensitive content transmitted outside the browser?

| Event | Text sent | Default |
| :--- | :--- | :--- |
| Prompt that broke a rule (BLOCK / WARN / REDACT / MONITOR) | Prompt with **credentials, connection-string passwords, crypto wallet keys, card, Aadhaar, IBAN, bank account, passport and voter ID numbers masked** (2.6 adds the last six). Emails, phone numbers, PAN, UPI IDs, GSTIN, internal IP addresses and keywords are **not** masked in this text. For REDACT, the redacted text that was actually sent. | **On** ("Store text of prompts that broke a rule") |
| Allowed prompt | Prompt with credentials/card/Aadhaar masked | **Off** (counted only) |
| File upload event | File names and sizes; never file content | Follows the first setting |
| Blocked website (own BLOCK list, unapproved AI tool) | Hostname | Always |
| Website blocked by category | Category only (no hostname) | Always |

When a setting is off, the extension omits the text and the server discards any text it receives anyway (`backend/app/core/privacy.py: prepare_prompt_for_storage`). The server re-masks the same items (credentials, connection strings, wallet keys, card, Aadhaar, IBAN, bank account, passport and voter ID numbers) before storing, whatever the client sends. Text pasted into an AI prompt box (2.6) is checked locally like a prompt; only a paste that a Block rule stops is reported, as a masked event like a blocked prompt.

## 6. Where are logs and security events stored?

In the database tables above. The extension writes only warnings without content to the browser console. **[deployment]** Your web server / Uvicorn access logs contain request paths; `GET /api/v1/events/users/{employee id}/status` puts the employee ID (the account email) in the URL, so access logs contain employee emails. Restrict and rotate those logs. In development without SMTP, invite, staff-invite and password-reset links are written to the backend console/log. `python -m app.cli create-platform-owner` prints the temporary password once to the terminal it runs in (not to the server log); it must be changed at first sign-in.

## 7. Who can access the collected data?

| Who | Access |
| :--- | :--- |
| Dashboard ADMIN of the account (individual account or company workspace) | Everything for that account; can change settings, buy plans and credits, set the monthly limit and cancel automatic renewal. The billing-history, receipt, subscription, usage and credit-ledger endpoints answer any signed-in account of the same organization, only with its own records (never another account's). The person who signs up becomes the admin of their own new individual account; accounts never see each other's data |
| Dashboard VIEWER | Read everything for that organization (events, prompt text as stored, audit log); cannot change anything |
| Dashboard EMPLOYEE | Only their own activation: generate activation codes, see and sign out their own browsers, and (through the API) their own usage counts. No organization data |
| Personal API token holder (2.1) | With `alerts:read`: the token's own account's security alerts (time, site, rule, category, severity, action, outcome, employee ID; **never prompt text**); with `usage:read`: its plan state, credit balance and daily prompt-check counts. Read-only; nothing else |
| AgentShieldAI staff (internal console, separate staff accounts with mandatory MFA; no customer role has platform access any more) | Per permission (`backend/app/core/permissions.py`, enforced by the server on every `/internal/*` request): all roles see every customer account's name and type, user accounts (emails, roles, status, verified), licences and licence history, usage counts (prompt checks per day) and the credit history (`companies.read`); browsers (name, OS, status, last seen) only with `devices.read` (owner, admin, security analyst, support agent); every company's orders, payments and the Razorpay webhook log only with `billing.read` (owner, billing admin, read-only analyst); the platform-wide audit log only with `audit.read` (owner, admin, security analyst); metrics with `metrics.read`. Changes: suspending companies/accounts, managing licences and removing credits (owner, admin), licence and credit exceptions and plans & pricing (owner only), refunds and reconciliation (owner, billing admin), staff management (owner only). Staff do not read prompt text or security events (no internal endpoint returns them; the Platform health page shows only counts) |
| Customer ADMIN / VIEWER: staff actions | Staff actions on an account (licence, credits, suspension, account changes) are recorded with that company's ID, so they also appear in that company's Admin Audit Log (actor `staff:<email>`) |
| Activated browser (device session) | Its organization's rules and its own account's status; can submit events attributed to its account; cannot read events |
| Database / server administrators **[deployment]** | Everything in the database |

## 8. Authentication, authorization, encryption, retention, deletion

* **Authentication:** accounts are created from an admin's email invite (joins the admin's company workspace), or by self sign-up on the dashboard login page, which creates a new **individual** account with that person as its ADMIN (`SIGNUP_ENABLED`, optionally limited to `SIGNUP_ALLOWED_DOMAINS`; disposable mailbox domains refused; company sign-up is refused unless `COMPANY_SIGNUP_ENABLED`). An invite verifies the address (the link goes to that inbox); self sign-up signs the person in at once and emails a single-use confirmation link, so the address is proven only when that link (or a password-reset link) is opened; the free trial requires it. An email that already has an account is refused at sign-up (HTTP 409), which reveals that the account exists; the sign-up rate limit limits such probing. Users sign in to the dashboard with email + password (PBKDF2-HMAC-SHA256, 600,000 iterations for new hashes; older hashes keep their own count), JWT HS256 valid `DASHBOARD_TOKEN_HOURS` (default 12 h). **Forgot password?** emails a single-use reset link (`#reset=…`, `PASSWORD_RESET_EXPIRE_MINUTES`, default 60) to any active account, with the same answer whether or not the email exists; using it marks the email as verified; setting a new password, changing it, or **Sign out everywhere** ends the account's other sessions. Browsers are activated once by pasting a single-use activation code (30 minutes) that a signed-in account generated, only while its company has an active licence; the code identifies that account, and the extension never handles a password; afterwards they obtain 15-minute sessions (`DEVICE_SESSION_MINUTES`, never past the licence end) by signing a one-time server challenge with their non-extractable private key. Every API call re-checks that the browser is active, the account enabled, the company not suspended and its licence active (trial, paid or internal) or prepaid credits available, within its included monthly checks and its own monthly limit. Personal API tokens (`aspt_…`, 2.1) authenticate only the read-only `/api/v1/public/*` endpoints of their own account.
* **Rate limits** (in memory, per server process): failed sign-ins (5 per account and 30 per IP per 15 minutes), activation attempts (10 per IP per hour), activation-code generation (5 per user per hour), sign-ups (10 per IP per hour), resends of confirmation links (3 per email and 10 per IP per hour), personal API token use (60 per minute per token) and creation (10 per person per hour), password-reset requests (3 per email and 10 per IP per hour), invite, confirmation and reset link checks, and challenge/session requests. Free-trial claims are limited in the database instead: a confirmed email is required, one per account and per normalized email, one per company email domain for company workspaces only (public webmail excepted), and `TRIAL_CLAIMS_PER_IP_30D` (3) per network (keyed IP hash) per 30 days. These raise the cost of repeated trials but cannot stop someone with new mailboxes and networks; AgentShieldAI staff can still grant or extend licences.
* **Internal staff authentication:** staff sign in to the separate internal console with email + password (at least 14 characters), then a 6-digit authenticator code (TOTP) or a single-use recovery code; no session is issued before that second step, and the first sign-in forces authenticator enrolment and shows 10 recovery codes once. Staff sessions last `STAFF_TOKEN_HOURS` (default 8 h). 5 failed passwords lock the email for 15 minutes; 30 sign-in attempts per IP per 15 minutes; 10 code attempts per staff member per 5 minutes (in memory, per process). Staff tokens (`typ=staff`) are refused by every customer API, and customer tokens by every `/internal/*` API.
* **Authorization:** role checks for customers (`get_current_admin`) and per-organization filtering on every customer query; for staff, one named permission per internal route (`require_staff`, `core/permissions.py`).
* **Encryption in transit [deployment]:** the application does not enforce HTTPS. You must serve the API and dashboard over HTTPS; development uses plain HTTP on localhost.
* **Encryption at rest [deployment]:** provided by your database host, not by AgentShield.
* **Retention:** security events older than the organization's retention period (default 30 days, set in the dashboard) are deleted at startup and at most hourly during ingestion. **The admin audit log, endpoints, governance records, accounts, invites, email confirmations and reset links, activation codes, devices, licences, licence changes, trial claims, notifications, billing orders, payments, subscriptions, webhook events, daily usage counts, the credit ledger, personal API tokens (also revoked or expired ones), staff accounts, staff recovery codes and staff invites have no automatic deletion** (revoked or used invites, links, codes and devices remain as records; a self-registered account and its company stay until deleted in the database, even if never used; trial claims are kept so a trial cannot be claimed again).
* **Deletion:** deleting an organization cascades to all its data (including its licences, trial claim, notifications, billing orders, payments and subscriptions, usage counts, credit ledger and API tokens; `webhook_events` are not tied to a company and stay; Razorpay keeps its own payment records under its own retention); deleting an account cascades to its email confirmations, reset links, activation codes, devices and API tokens. There is no dashboard function to erase one employee's records (for a data-subject request, delete their rows from `security_events`, `endpoints`, `user_governance`, `usage_daily`, `user_invites` and `users` in the database).

## 9. What happens when the extension is offline?

AgentShield fails closed. While the current session (up to 15 minutes) is still valid, rules, keywords and website lists from the last sync keep being enforced. Once the session cannot be renewed because the server is unreachable, the browser locks: every AI site shows the **Activation Required** page until the server can be reached again (the activation itself is kept, so no new code is needed). Events are kept in the local queue (max 500; the oldest are dropped beyond that) and sent after the next successful sync. Heartbeats are skipped, so the browser shows as "Not seen today" in the dashboard.

Queued events are counted as prompt checks when they arrive (once each, by their event ID). The same applies when the account's licence ends, is revoked, its included checks, credits or own monthly limit run out, or the account is suspended: the server refuses the next request, the browser locks (popup **Your plan has ended** or the reason) but keeps its activation, and it reconnects by itself once a licence is active again. Expiry is decided by server time, not the PC's clock.

**Free plan (2.3).** An individual account with a confirmed email and no live plan is on the Free plan instead of locked. When its free monthly prompt checks (or its own monthly limit) are used up and no credits remain, the browser stays connected and website controls keep working, but the extension **stops inspecting prompts and sends no prompt events** (so nothing is stored or metered for them) until the checks reset on the 1st (UTC), the plan is upgraded or credits are added. The popup and the in-page badge say "Protection paused".

## 10. How can an administrator audit and verify these behaviours?

1. **Admin Audit Log** page: every configuration change with before/after values, sign-ins and exports.
2. **Prompts & Risk Events** → open an event: shows exactly what text was stored.
