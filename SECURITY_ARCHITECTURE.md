# AgentShield — Security Architecture

This document describes the components, trust boundaries, how each control is enforced, and what is **not** enforced. Every statement here is checked against the code at version 2.1.0 (SaaS phase 1: companies, free trial, licences; SaaS phase 2: Razorpay payments; 1.5.1: sign-up without email confirmation; 2.0.0: separate internal admin console with staff roles and mandatory MFA, no built-in credentials; 2.1.0: Individual accounts (Company coming soon), email confirmation before the trial, usage metering, prepaid credits and limits, personal API tokens); file references are given so a reviewer can verify them.

---

## 1. Components

| Component | Runs where | Code | Role |
| :--- | :--- | :--- | :--- |
| Browser extension (MV3) | Each employee's Chrome / Edge / Brave | `extension/` | Inspects prompts and uploads on AI sites, blocks websites, reports events |
| AgentShield Windows app (2.4) | Each Windows PC where `AgentShield-System-Setup.exe` was installed; runs as the signed-in Windows user | `scripts/helper/AgentShieldHelper.cs` | Connects the PC once with a portal activation code, then hands each browser on the PC a fresh single-use activation code (native messaging host `com.agentshield.helper`, `agentshield://` link handler) |
| Policy & audit API (FastAPI) | Your server | `backend/app/` | Stores rules, keywords, settings, events, audit log; authenticates accounts and authorizes browsers |
| Database (PostgreSQL / Supabase, or SQLite for development) | Your database host | `backend/app/db/models.py` | Persistence |
| Customer portal / admin dashboard (React) | Customer operators' and employees' browsers, served as static files | `dashboard/` | Configuration, investigation, invites (company workspaces), browser activation codes, plan and credit purchase, usage, personal API tokens. Contains no platform (cross-company) pages |
| Internal admin console (React) | AgentShieldAI staff browsers, static files on **their own origin** (dev: `http://localhost:5175`) | `admin-console/` | Companies, licences, payments, plans & pricing, extension releases, platform audit log, staff & roles. Talks only to `/internal/*` with a staff session |
| Razorpay (external payment processor) | Razorpay's servers; hosted Checkout loaded from `checkout.razorpay.com` in the admin's browser | `backend/app/core/razorpay.py`, `dashboard/src/services/razorpayCheckout.ts` | Collects card/UPI details, holds orders, subscriptions, payments and refunds; sends signed webhooks. Contacted only when `RAZORPAY_KEY_ID` and `RAZORPAY_KEY_SECRET` are set |

## 2. Trust boundaries

```
 [Employee browser]                                [Your server]                 [Database]
  content script (untrusted page context)           FastAPI                       PostgreSQL / Supabase
      │  chrome.runtime messages                       │                             ▲
      ▼  (sender.id checked)                           │  SQLAlchemy (owner role)    │
  service worker ── HTTPS + device session JWT ───────►│─────────────────────────────┘
      │  signs challenges with a non-extractable key   ▲
      ▼  (IndexedDB, never leaves the browser)         │
 [Operator / employee browser] dashboard ── HTTPS + account JWT (typ=user) ──► /auth/*, /api/v1/*
 [AgentShieldAI staff browser] admin-console (own origin) ── HTTPS + staff JWT (typ=staff, after MFA) ──► /internal/*
```

| Boundary | Threat | Control |
| :--- | :--- | :--- |
| AI website ↔ content script | Page script tampers with or spoofs messages | Content scripts run in an isolated world; the service worker accepts messages only from this extension (`sender.id === chrome.runtime.id`), and account actions (`ACTIVATE`, `SIGN_OUT`) only from the extension's own pages, never from content scripts (`service-worker.ts: handleMessage`). The block page (`blocked.html`) can be opened by any site, so the worker only logs a domain that its own rules actually block. |
| Distribution ↔ access | Copied extension, files, storage or codes used to gain access | Installing or enabling grants nothing. A browser is authorized only by a single-use activation code (30 min) that an active (not disabled) account generated while signed in to the dashboard; the code identifies that account and is consumed together with the browser's new device public key (`api/device_auth.py: activate`). The private key is a non-extractable WebCrypto ECDSA P-256 key in IndexedDB (`shared/device-identity.ts`), so copying the extension folder or `chrome.storage` yields no usable credential, and a used code cannot be reused. An unused code is a bearer secret for its 30 minutes: whoever pastes it first connects a browser to that account (users are told not to share it; "Require admin approval for new browsers" adds a second check). |
| Browser ↔ API | Stolen or forged device credential | Each 15-minute device session (`DEVICE_SESSION_MINUTES`) is issued only after the browser signs a one-time, 60-second server challenge with its private key; nonces cannot be replayed (`device_auth.py: challenge, session`). Every request re-checks that the device is ACTIVE and the account and organization are active (`api/deps.py: _device_from_payload`), so revocation and account disabling take effect at the next request. Sessions are JWTs with `typ=device`, bound to device, account and organization; dashboard tokens and challenge nonces are not accepted as sessions. A device can only read policies/domains/keywords/settings, read its own account's governance status, submit events and heartbeats, and sign itself out. Rate-limited per device. |
| Windows app ↔ API ↔ browsers (2.4) | A PC connection used to connect browsers elsewhere; a web page connecting a PC to an attacker's account; a revoked browser reconnecting by itself | The PC is connected only with a single-use portal activation code (`POST /api/v1/computer/activate`, same checks as browser activation: active account, active plan, free device slot, `MAX_DEVICES_PER_USER`). The app creates an ECDSA P-256 key in the **Windows user's** CNG key store with export disabled; the server stores only its public key. A browser code (`POST /api/v1/computer/browser-code`, single-use, 5 minutes, only the newest is valid) is issued only for a fresh 60-second challenge (`typ=computer_challenge`, distinct from device challenges, never replayable) signed with that key, so copying `pc-connection.json` (server, PC id, email only) to another PC yields nothing. The browser then activates through the normal `/api/v1/device/activate` with its own key, so every browser keeps its own 15-minute sessions and every request is re-checked; a browser code cannot connect another PC. Only the extension IDs listed in the native messaging manifest (written by the installer, HKLM, admin only) can talk to the app, and the app's answer is only a code the extension activates with: nothing the app returns sets the authorized state. `agentshield://connect?code=…` links (portal "Connect this PC") always show a confirmation window with the server address before connecting, and a PC set up for a server (`HKLM\SOFTWARE\AgentShield\ServerUrl`) refuses codes for another server. Removing a PC (portal, app "Disconnect", uninstall) revokes the PC and all its browsers at once (`api/computers.py: revoke_computer`); signing out one of its browsers in the portal removes the whole PC, because the app would otherwise reconnect it; "Sign out this browser" in the extension stops it from asking the app again until the person clicks "Connect" in the popup. A PC holds at most `MAX_BROWSERS_PER_COMPUTER` browsers (the least recently seen is replaced). Connections, browser codes, refusals and disconnects are audited. |
| Browser ↔ API | Event or heartbeat attributed to someone else | The organization and the employee come from the authorized device's account; payload `organization_id`, `company_name`, `user_id` and `device_id` are ignored (`deps.py: employee_id_for`, `events.py: ingest_event`, `endpoints.py: heartbeat`). |
| Licence ↔ access | Using the extension without a paid or trial entitlement; bypassing expiry | Every activation, session issue and extension API call evaluates the company's licence with the **server's clock** (`core/entitlements.py: current_entitlement`, called from `api/deps.py` and `api/device_auth.py`); refusals carry NO_LICENSE, LICENSE_EXPIRED, LICENSE_REVOKED or ORG_SUSPENDED, and since 2.1 USAGE_LIMIT (the plan's included monthly prompt checks are used up and no credits remain), SPEND_CAP (the account's own monthly limit) or NO_CREDITS (pay-as-you-go credits used up). The decision uses only server records: licences, `organizations.credit_balance`, `monthly_check_cap` and the metered usage of the current UTC month (`usage_daily`). A device session's lifetime is capped at the licence end. Activation codes are only issued with an active licence or credits. Nothing the browser sends (dates, flags, cached states) is trusted, so changing the computer clock, reinstalling or editing storage cannot restart or extend a trial. A scheduled job only sends reminders; it never decides access. |
| Free trial ↔ API | Repeated trials | One trial per account (UNIQUE `trial_claims.organization_id`) and per normalized email (UNIQUE; Gmail dots/`+tags` folded); for **company workspaces** also one per company email domain (public webmail excepted; individuals are limited per person instead); disposable mailbox domains refused; a per-network cap using a keyed hash of the IP (`core/abuse.py`, `api/billing.py: trial_eligibility`). Since 2.1 the claimant's **email must be confirmed** (single-use emailed link) before a trial is granted, so the per-email rule counts only addresses the claimant controls. Concurrent claims are stopped by the database constraints. |
| Usage metering ↔ API (2.1) | Using more than paid for; double counting or double spending; client-set balances | The billable unit is a prompt check reported by an **activated browser** (`api/events.py` meters only when the caller is a device session; dashboard tokens are not metered); website blocks (`dlp.*`) and file events are excluded (`core/usage.py: is_prompt_check`). Each extension event carries a random `client_event_id` stored with UNIQUE (organization, client_event_id), so retries and offline replays are stored and metered once. Credits are spent with one atomic `UPDATE … SET credit_balance = credit_balance - 1 WHERE credit_balance > 0` (never twice, never below zero; on Supabase the 2.1 migration also adds a CHECK constraint forbidding negative balances); every other balance change is written to `credit_ledger`. Balances, usage and limits change only on the server: request fields such as `credit_balance` are ignored. Access is re-decided on every request, so a browser locks at its next request once checks, credits or the account's own cap are used up. The server sees only what extensions report: see §5. |
| Account types ↔ API (2.1) | An individual account managing other people | Public sign-up creates `INDIVIDUAL` accounts; `COMPANY` sign-up is refused (403 `COMPANY_COMING_SOON`) unless `COMPANY_SIGNUP_ENABLED`. Company-management routes (`/api/v1/org/users`, invites, `/api/v1/org/devices`) use `require_company_workspace` (`api/deps.py`) and refuse individual accounts with 403 `COMPANY_FEATURE_UNAVAILABLE`; the portal also hides them. Existing company tenants keep them. |
| Personal API tokens ↔ API (2.1) | Token theft or misuse beyond its purpose | `aspt_…` tokens are random, shown once, stored only as SHA-256 hashes, created by a signed-in admin or viewer for their own account (`api/api_tokens.py`), at most 10 active, optional expiry (default 90 days), revocable at once. They are accepted only by `GET /api/v1/public/alerts` (`alerts:read`) and `/api/v1/public/usage` (`usage:read`), are read-only, limited to the token's own account (the owner must still be active and the account not suspended), rate-limited to 60 requests per minute per token, and never return prompt text. Every other dependency rejects them (they are not JWTs), so they get 401 on dashboard, extension and internal APIs. Creation and revocation are audited. |
| Payments: browser ↔ API ↔ Razorpay | Plan activated without paying (forged "paid" result, replayed or wrong-amount payment); card data exposure | The browser never decides a payment. The server creates the Razorpay order (one-time plans) or subscription (monthly) with the key secret, which never leaves the server; the browser receives only the public key id and the order/subscription id, and card/UPI details are entered in Razorpay's hosted Checkout, never in AgentShield. A plan activates, or a credit pack's credits are added, only in `core/payments.py: fulfil_payment`, from a payment Razorpay reports as `captured` for exactly the order's amount and currency, reached either by `/checkout/confirm` (the checkout HMAC-SHA256 signature with the key secret must match **and** the payment is then fetched from Razorpay's API; an `authorized` payment is captured by the server) or by a webhook. Mismatched amounts or currencies are ignored and audited (`billing.amount_mismatch`); invalid confirmation signatures are refused and audited (`billing.confirm_refused`). UNIQUE `billing_payments.provider_payment_id` makes checkout, webhook and reconciliation idempotent: one payment, one licence. Orders, subscriptions, confirmations, history and receipts are filtered by the caller's company; only company admins can buy or cancel (`api/payments.py`). |
| Razorpay webhook ↔ API | Forged or replayed payment events | `POST /api/v1/billing/razorpay/webhook` rejects any body whose `X-Razorpay-Signature` is not the HMAC-SHA256 of the raw body with `RAZORPAY_WEBHOOK_SECRET` (no secret configured = every webhook rejected). Each event id (`X-Razorpay-Event-Id`, or a hash of the body) is stored with a UNIQUE constraint in `webhook_events` and applied once; a processing error returns 500 and is recorded so Razorpay's retry reprocesses it. A full refund or an opened dispute revokes the licence the payment created, or removes the credits the pack added (never below zero, so credits already used are not taken back); a won dispute restores it; a partial refund keeps it. |
| Customer ↔ internal console | A customer (any role) administers other companies, plans or licences | Platform administration is no longer a customer role: the former `SUPERADMIN` role was removed (existing rows are converted to `ADMIN` of their own company at startup, `db/seed.py: init_db`, and by `migrations/2026_10_internal_console.sql`). Platform pages live in a separate app (`admin-console/`) on its own origin and call only `/internal/*`. Staff are separate accounts (`staff_users`), never rows in `users`. Token types are separate: customer `typ=user`, device `typ=device`, staff `typ=staff`; the sign-in step tokens `typ=staff_mfa` / `typ=staff_mfa_setup` are not sessions. Every `/internal/*` dependency accepts only `typ=staff` (`core/permissions.py: staff_from_token`), so customer and device tokens get 401 there; every customer dependency accepts only `typ=user` / `typ=device` (`api/deps.py`), so staff tokens get 401 on customer APIs (`tests/test_internal.py`). |
| Staff sign-in ↔ internal API | Stolen staff password; replayed codes; brute force | Password → authenticator (TOTP) code or single-use recovery code → session (`api/staff_auth.py`). `/internal/auth/login` never returns a session, only a short step token (5 min, or 10 min for enrolment). A staff member without an authenticator must enrol one first (QR code or manual key; the QR is drawn in the browser from the `otpauth://` URI, no third-party service) and is shown 10 single-use recovery codes once. `get_staff_session` refuses any session whose account has no enrolled authenticator. TOTP: RFC 6238, 6 digits, 30 s, ±1 step; the last accepted step is stored so a code cannot be replayed (`core/totp.py`). Authenticator secrets are encrypted at rest with Fernet (key from `STAFF_MFA_KEY`, or derived from `SECRET_KEY` with HKDF; rotating `SECRET_KEY` without `STAFF_MFA_KEY` makes the stored secrets unreadable, so authenticator codes stop working; staff then sign in with a recovery code and an owner resets the others' authenticators, while an owner's own authenticator must be reset by another owner). Recovery codes are stored only as SHA-256 digests bound to the staff account (`api/staff_auth.py: _recovery_hash`, digest of staff ID + normalized code; the codes are random, about 59 bits, so a fast digest suffices; not a password hash) and marked used. 5 failed passwords for an email lock it for 15 min; 30 attempts per IP per 15 min; 10 code attempts per staff member per 5 min. Wrong email and wrong password give the same answer. Staff passwords: at least 14 characters. Sessions last `STAFF_TOKEN_HOURS` (8 h default) and carry a session version: password change, "sign out everywhere", a role change, disabling, an MFA reset and "end sessions" end existing sessions immediately. A temporary (bootstrap) password must be changed before any other internal API works (403 `PASSWORD_CHANGE_REQUIRED`). Every step (success, failure, lockout, enrolment, recovery-code use) is audited with `actor_type=staff`. |
| Staff roles ↔ internal API | A staff member does more than their role allows | Every internal route declares one permission with `require_staff("<permission>")`; a role name alone grants nothing. Roles map to permissions only in `STAFF_PERMISSIONS` (`core/permissions.py`; table in README "Authentication model"); `tests/test_internal.py` checks every permission for every role. Company detail includes browser details only for roles holding `devices.read`. The console hides buttons the role lacks, but the server is the only enforcement. |
| Licences ↔ internal API | Paid access granted without payment | Paid entitlements normally come only from verified payments (`core/payments.py`). Granting a PAID or INTERNAL plan, or extending any non-trial licence, without a verified payment is an **exception**: it needs `licenses.exception` (platform owner only) and a reason. A granted exception is stored with `payment_ref = exception:<staff email>` and audited as `platform.license_exception`; an extension is audited as `platform.license_extend` with before/after dates. Trial grants and trial extensions need `licenses.manage`. Every grant and extension also writes `license_adjustments`. Refunds (`/internal/api/billing/payments/{id}/refund`, `billing.refund`) require a reason, are sent to Razorpay and audited (`billing.refund_requested`); the licence changes only when Razorpay reports the refund (immediately if Razorpay answers `processed`). Reconcile (`billing.reconcile`) re-checks recent unpaid one-time orders with Razorpay and audits the run. |
| Staff accounts ↔ internal API | Unauthorised staff accounts; losing the last administrator | No staff credentials exist in source or configuration. The first platform owner is created only by `python -m app.cli create-platform-owner --email …` (`app/cli.py`), which prints a random temporary password once (stored only as a hash), forces a password change and authenticator enrolment at first sign-in, and refuses when an owner already exists unless `--force`. Further staff only by owner invite (`/internal/api/staff/invite`, `staff.manage`): a single-use 48-hour link (`#staff-invite=ast_…`, token in the URL fragment, stored only as a SHA-256 hash), emailed; in development without SMTP the link is written to the server log, in production without SMTP the invite is refused. The owner can change roles, disable, reset MFA and end sessions; the last active owner cannot be demoted or disabled, and an owner cannot reset their own authenticator. All of this is audited with `actor_type=staff` (`api/staff_admin.py`). |
| Built-in credentials | Anyone who read the repository signs in | No default admin, no default `SECRET_KEY`, no demo logins in the portal. The first customer company and its admin are created only when both `INITIAL_ADMIN_EMAIL` and `INITIAL_ADMIN_PASSWORD` are set (≥ 14 characters in production). `SECRET_KEY` is required in production (refused if missing, shorter than 32 characters or a published default); in development without it a random key is generated per process (sessions end on restart). A read-only demo auditor exists only when `DEMO_AUDITOR_PASSWORD` is set, never in production (disabled at startup there). Passwords published by older releases are refused as new passwords and flagged (`api/auth.py`). `tests/test_no_hardcoded_secrets.py` scans shipped source for live keys, secret tokens, env defaults for secrets and those published passwords (allowed only in the deny-lists in `api/auth.py` and `core/config.py`). `SUPABASE_SETUP.sql` still inserts demo accounts with published passwords for local testing only; do not use it as-is for production. |
| Accounts ↔ API | Account creation by outsiders; stolen sessions | Accounts come from self sign-up or, in company workspaces, an admin's emailed invite. Self sign-up (optional name, email, password) creates a new **individual** account with the person as its `ADMIN` and signs them in at once (201 with a session); it also emails a single-use confirmation link (`#verify=asv_…`, `EMAIL_VERIFY_EXPIRE_HOURS`, stored as a SHA-256 hash; `/auth/verify-email` sets `email_verified_at`, `/auth/resend-verification` sends a new one with the same answer either way). The address is therefore not proven at sign-up: a confirmed email is required only to claim the free trial, not to sign in, buy, generate activation codes or activate. A password-reset link also confirms it. Disabled accounts are refused everywhere. Dashboard JWTs carry a session version: password change/reset and "sign out everywhere" invalidate older tokens; sign-ins last 12 h. Password reset uses a single-use 60-minute emailed link, works for any active account, gives the same answer whether or not the account exists, marks the email verified when used, and ends all other sessions (so the real owner of a squatted address can take the account over). Self sign-up can be limited to company email domains (`SIGNUP_ALLOWED_DOMAINS`) or turned off (`SIGNUP_ENABLED=false`); disposable mailbox domains are refused. Invites are single-use (72 h). Only SHA-256 hashes of link tokens are stored and tokens travel in the URL fragment. Sign-up refuses an email that already has an account with 409 ("Sign in, or use Forgot password"), which reveals that the account exists; the sign-up rate limit limits such probing (`api/auth.py`; `api/users.py: invite_user`). Each account only ever sees its own data; invited EMPLOYEE accounts can only generate codes and see their own browsers. |
| Accounts ↔ API | Password guessing, stolen session | PBKDF2-HMAC-SHA256 passwords (600,000 iterations for new hashes); 5 failed sign-ins lock an account for 15 min and 30 failures per IP block that address; activation is limited to 10/h per IP; sign-up to 10/h per IP; code generation to 5/h per account; JWT (HS256) with expiry; production refuses default secrets (`core/config.py`, `core/ratelimit.py`). Sign-ins, failures, lockouts, sign-ups, password resets, invites, activations (and refused activations), approvals and revocations are audit-logged. Disabled accounts cannot sign in; a confirmed email is required only for the free trial. |
| Employee accounts ↔ organization data | Employee reads events, settings or other employees' data | `EMPLOYEE` accounts pass only `get_signed_in_user` (own profile, password, activation codes, own devices). Every data endpoint uses `get_current_user`, which accepts operators only; `get_principal` refuses employee tokens (`api/deps.py`). |
| API ↔ Database | Data exposed through Supabase's REST API | Row Level Security is enabled on every table at startup on PostgreSQL (`db/seed.py:_align_schema`) and in the SQL migrations. The backend connects as table owner, which bypasses RLS. |
| Stored data | Audit DB becomes a store of secrets | Secrets, card and Aadhaar numbers are masked in the browser and again on the server before storage (`core/privacy.py`). Invite and activation tokens are stored only as SHA-256 hashes and shown once; device private keys never reach the server. |

## 3. Enforcement mechanisms

| Control | Type | How it is enforced | Code |
| :--- | :--- | :--- | :--- |
| Activation gate (fail closed) | **Block** | The service worker always starts `LOCKED` and only a server-issued, unexpired session makes it `AUTHORIZED`; nothing read from storage sets that state. While not authorized, every AI site is redirected to an "Activation Required" page by network rules (above Allow rules), the `document_start` script and `tabs.onUpdated`; the content script also refuses to send any prompt or file. States: `LOCKED → CONNECTING → AUTHENTICATING → TRIAL_ACTIVE | SUBSCRIPTION_ACTIVE` (only with the server's licence verdict; the server state `CREDITS_ACTIVE` unlocks as `SUBSCRIPTION_ACTIVE`), failures `EXPIRED` (plan ended, or `USAGE_LIMIT` / `SPEND_CAP` / `NO_CREDITS`; the device identity is kept), `REVOKED`, `CONNECTION_ERROR`, `INVALID_TOKEN`, `PENDING_APPROVAL`. | `background/auth-state.ts`, `service-worker.ts`, `shared/domains.ts`, `content.ts: gateSubmission, checkFiles` |
| Device approval | Block (optional) | With "Require admin approval for new browsers", a newly activated browser stays `PENDING` and gets no session until an admin approves it. | `device_auth.py`, `users.py: approve_device` |
| Prompt inspection | **Block / Redact / Warn / Monitor** | Capture-phase listeners for `keydown` (Enter and Ctrl/Cmd+Enter), send-button `click` and form `submit` stop the event before the site's own handlers run. | `content/content.ts` |
| Bypass resistance | Block | After a WARN is confirmed or a REDACT applied, only that exact text is approved, once, for 5 s. While an AgentShield dialog is open every page submission is held. Redaction is verified by reading the prompt box back; if masking did not take effect the prompt is blocked. | `content.ts: isApproved, gateSubmission, handlePolicyAction` |
| File uploads | Block / Warn / Monitor | `input`/`change` on file inputs, `drop` and `paste` with files are stopped, checked, and re-dispatched only if allowed. Text files ≤ 2 MB are scanned with the prompt rules; a REDACT match blocks the file. | `content.ts: attachFileInterception, checkFiles` |
| Website blocking | Block | `declarativeNetRequest` dynamic redirect rules (main frame, domain + subdomains). Backups: `document_start` content script and `tabs.onUpdated`. Precedence: explicit block > activation lock > allow > unapproved AI. | `shared/domains.ts`, `service-worker.ts: applyBlockingRules` |
| Unapproved AI tools | Block (optional) | When enabled, known AI domains not on the Allowed list are blocked. | `core/catalog.py: KNOWN_AI_DOMAINS` |
| Website categories | Block (per category) | Malware/phishing/scams, adult, piracy (on by default), gambling, social networks, filter bypass, movies/music & streaming (AgentShield's own list only). AgentShield's own additions (`web-category-additions.json`: exact domains, and site names matched as plain `||name` domain anchors, never regexes) are rules with id ≥ 1000 in the same rulesets. Domain lists ship inside the extension as `declarativeNetRequest` static rulesets (priority 1, main and sub frames), switched on with `updateEnabledRulesets` from the server's settings; missing or malformed settings fall back to the defaults, never to "all off". An ALLOW rule (priority 2) is the exception mechanism; explicit BLOCK and the activation lock still win. A never-block list (Google, Microsoft, Apple, Amazon, GitHub, Wikipedia, the AI sites, …) is removed from the lists when they are generated. | `shared/web-categories.ts`, `scripts/update-web-categories.js`, `core/catalog.py: WEB_CATEGORIES`, `api/organization.py` |
| Safe Search | Enforce (follows adult blocking unless set) | Dynamic rules add `safe=active` (Google), `adlt=strict` (Bing), `kp=1` (DuckDuckGo) to search URLs (a higher-priority allow rule for URLs that already have it prevents loops) and set the `YouTube-Restrict: Strict` request header. | `shared/web-categories.ts: safeSearchRules` |
| Employee governance | Block | SUSPENDED blocks every prompt and upload; RESTRICTED turns every WARN into BLOCK. Status cached 30 s. | `shared/policy.ts: evaluateFindings` |
| Policy precedence | — | BLOCK > REDACT > WARN > MONITOR > ALLOW, ties by severity; same logic in browser and server. | `shared/policy.ts`, `policies/evaluator.py` |
| Usage limits and credits | Block | Each request re-evaluates the plan's monthly included checks, the credit balance and the account's own cap; credits are spent atomically per metered check; events are metered once per `client_event_id`. | `core/entitlements.py: current_entitlement`, `core/usage.py`, `api/events.py` |
| Free plan and referrals (2.3) | Server-computed | The Free plan is never a licence or a purchase: it is derived on every request from server data (account type, confirmed email, no live licence, `FREE_TIER_ENABLED`). Connection gates (`get_principal`, device activation and session, activation codes) accept `ACCESS_STATES` (active states + `FREE_PAUSED`); nothing the browser sends selects a state. Referral bonuses are granted only by the server when the invited person confirms their email (conditional UPDATE, once), capped per account (`REFERRAL_MAX`), not for the same person (normalized email) and not for company workspaces; `GET /api/v1/referrals` returns only the caller's own account. | `core/entitlements.py`, `core/referrals.py`, `api/auth.py: verify_email`, `api/referrals.py` |
| Paid licence activation | Block | No licence (or credits) from a payment unless Razorpay reports it captured for the exact amount/currency, verified by signature + server fetch or by HMAC webhook; idempotent per payment id and webhook event id. Paid time bought early starts after the paid time already bought. | `core/payments.py`, `api/payments.py`, `core/razorpay.py`, `core/entitlements.py: grant_license` |
| Admin audit trail | Detect | Every change (with before/after), sign-in, lockout, export, invite, activation, approval and revocation is written to `admin_audit_log`; payments add `billing.checkout`, `billing.confirm_refused`, `billing.payment_captured`, `billing.amount_mismatch`, `billing.refund`, `billing.refund_requested`, `billing.dispute_created/won/lost`, `billing.subscription_cancel`, `billing.reconcile`. ### Definitions used in the product

| Term | Meaning |
| :--- | :--- |
| **Detection** | A rule matched (always local). |
| **Monitor** | Allowed, but an event is recorded. The employee sees nothing. |
| **Warn** | Held until the employee confirms; an optional reason is recorded. |
| **Redact** | Matches are replaced with `[REDACTED:<CATEGORY>]` and the employee confirms the masked text. |
| **Block** | Not sent. The employee sees why and what to do. |
| **Activation** | Binding one browser to one account: a single-use code generated by the signed-in account + the browser's device key pair. |

## 4. Failure behaviour

| Situation | Behaviour |
| :--- | :--- |
| Never activated | AI sites blocked ("Activation Required"); no rules synced, nothing reported. Popup shows the activation screen. |
| Company's trial or plan ended | Every request is refused with LICENSE_EXPIRED; the browser locks (state EXPIRED, AI sites blocked) but keeps its device identity. Popup shows "Your plan has ended" with "Choose a plan" and "Check again". When a new licence is active the same browser reconnects by itself (5-minute check) — no reinstall. |
| Licence revoked / company suspended | LICENSE_REVOKED / ORG_SUSPENDED: locked like an expired plan until AgentShieldAI staff restore access. |
| Individual's trial or plan ended (2.3) | An `INDIVIDUAL` account whose admin confirmed their email moves to the **Free plan** (`FREE_ACTIVE`, computed in `core/entitlements.py`, no licence row): browsers stay connected with the free monthly prompt checks (300 by default) on 1 browser (more while prepaid credits remain). Company workspaces, unconfirmed accounts and accounts whose licences were all revoked do not get it. |
| Free monthly checks or own limit used up (2.3) | `FREE_PAUSED`: the device session stays valid (`ACCESS_STATES`), AI sites stay usable and website controls and category blocking keep working, but the extension stops inspecting (and metering) prompts and the popup says "Protection paused". Prompt checks resume by themselves on the 1st (UTC), after an upgrade, credits or a higher own limit; the extension learns the verdict at its next policy sync (≤ 5 min) or session. Unknown entitlement states still lock (fail closed). |
| Included checks, credits or own monthly limit used up | USAGE_LIMIT / NO_CREDITS / SPEND_CAP at the next request after the limit is reached: locked like an expired plan (identity kept). After a top-up, an upgrade, a higher or removed limit, or the next UTC month (included checks and own limit), the same browser reconnects by itself. |
| Backend unreachable | A live session stays valid until it expires (at most 15 minutes); renewal is retried after 2 s, 8 s and 30 s, then every 5 minutes or on "Retry". When the session expires without renewal, the browser locks (`CONNECTION_ERROR`) and AI sites are blocked. There is no offline bypass. Events are queued (max 500, oldest dropped) and sent after the next successful sync. |
| Browser restarted | The session (kept only in memory and `chrome.storage.session`) is gone; the worker starts `LOCKED` and signs a new challenge before unlocking. |
| Device revoked, account disabled | The next request is refused (401); the browser locks, deletes its key and must be activated again with a new code. |
| Pending approval | Locked until an admin approves; the popup says so. |
| Prompt box not found (site layout changed) | Prompts are **not** checked on that page; the in-page badge shows "Not Protected". |
| Database unavailable | `/health/ready` returns 503; API calls fail; browsers lock when their sessions expire. |
| Razorpay keys not configured | Checkout returns 503 and the portal shows "Contact AgentShield"; no request is made to Razorpay; webhooks are rejected without `RAZORPAY_WEBHOOK_SECRET`. |
| Checkout tab closed or confirmation fails after paying | Nothing is granted by the browser; the payment is completed by the webhook (or by staff's Reconcile for one-time orders) once Razorpay reports it captured. |
| Webhook processing error | Returns 500 and is logged as `failed` in the webhook log; Razorpay retries and the retry reprocesses the event. |
| Monthly renewal fails | No new paid period is granted without a captured charge; the plan ends at its end date and the browser locks as for an expired plan. |

## 5. Limitations (not enforced)

| Gap | Why | What closes it |
| :--- | :--- | :--- |
| Other browsers, desktop/mobile AI apps, scripts and API calls | Out of reach of a browser extension | Allow only managed Chrome/Edge (AppLocker / Intune), DNS or proxy filtering of AI domains |
| Employee disables or removes a self-installed extension | Extensions installed from a .zip or "Load unpacked" can be removed; AI sites are then simply unprotected | Force-install via `ExtensionInstallForcelist` (Group Policy, Intune, Google Admin); see DEPLOYMENT.md |
| Local modification of the extension | A user with developer mode can edit a self-installed extension's code and skip the activation screen. The server still refuses rules and reports without a valid device session, so that browser never appears as protected. | Force-install (users cannot edit it) and `DeveloperToolsAvailability` policy on managed devices |
| Copying a whole browser profile | Copying the entire Chrome profile folder (including IndexedDB) can carry the non-extractable key to another PC | Per-device revocation in Users & Devices; watch "last seen" for duplicates; managed devices |
| Developer tools | A technical user can remove listeners | `DeveloperToolsAvailability` policy on managed devices |
| PDF / Office / image content | Not parsed in the browser | Only the `file.upload` rule applies; add a server-side or endpoint DLP if required |
| Obfuscated or semantic leaks | Pattern-based detection | ML / exact-data-match classifiers (not implemented) |
| Second factor (customer accounts) | Customer accounts use email + password; invites verify the email, self sign-up verifies it only when the emailed confirmation link is opened (required for the trial). (Internal staff accounts require an authenticator app.) | SSO / MFA for customer accounts (not implemented) |
| Staff MFA strength | Staff MFA is TOTP (authenticator app) with recovery codes; no hardware-key / WebAuthn option, so a staff member can be phished for a live code | WebAuthn / passkeys for staff (not implemented); keep the console on its own origin and train staff |
| Staff session in the console | The staff session token is kept in `sessionStorage` (cleared when the tab closes); an XSS in the console would expose it. The console loads no third-party scripts (only Google Fonts stylesheets) | Short `STAFF_TOKEN_HOURS`; "Sign out everywhere"; an owner can end a staff member's sessions; a strict CSP on the console's web server |
| Internal console scope | Phase A plus the 2.1 Accounts and Platform health pages: no customer analytics, support tooling or further operations pages yet (Phases B–D); INTERNAL licences still exist for the initial company created from `INITIAL_ADMIN_*` | Later phases |
| Open sign-up | With `SIGNUP_ENABLED` and no domain list, anyone with a confirmed email address can create their own individual account and claim one free trial (they never see other accounts' data) | Intended for a public SaaS; set `SIGNUP_ALLOWED_DOMAINS` or turn sign-up off for a private deployment |
| Sign-in before email confirmation | Sign-up signs the person in before the email is confirmed, so anyone can create an account with an address they do not own. They cannot claim the free trial with it (that needs the emailed link), but they can buy plans or credits and use them. A squatted email blocks the real owner's sign-up with 409; the real owner can take the account over with Forgot password (the reset link goes to their inbox), which also ends all other sessions. Sign-up is enumerable (409 reveals an existing account), limited by the sign-up rate limit (10 per IP per hour, per process) | AgentShieldAI staff can suspend squatting accounts; `SIGNUP_ALLOWED_DOMAINS` or `SIGNUP_ENABLED=false` on private deployments |
| Usage metering is client-reported | The server meters what activated extensions report. A user who modifies a self-installed extension could stop reporting checks (under-reporting); the server cannot see prompts that are never reported. Protection, however, stops server-side when access ends (no session, rules or sync once the plan, checks, credits or cap run out). The offline queue keeps at most 500 events (the oldest are dropped), so long offline periods can lose events and usage. Usage months are UTC calendar months. Extensions older than 1.5.0 send no `client_event_id`, so only identical submissions within 3 seconds are deduplicated for them | Force-install the extension (users cannot edit it); keep extensions current |
| Free plan and referral abuse (2.3) | Free use needs a confirmed email, and one person can create several free accounts with different mailboxes (each gets its own monthly free checks and 1 browser). A paused free account's extension stops checking prompts; a modified extension could keep checking locally (it cannot raise the server's counts or credits). Referral bonuses are limited to `REFERRAL_MAX` per account and to confirmed, different (normalized) emails, but two mailboxes of one person still count as two people. Referral credits, like purchased credits, keep `CREDITS_DEVICE_LIMIT` browsers while they last | Disposable-mailbox list at sign-up; staff can suspend abusing accounts or set `FREE_TIER_ENABLED=false` / `REFERRAL_BONUS_CHECKS=0` |
| No email confirmation (2.4.1 default) | With `EMAIL_VERIFICATION_REQUIRED=false` the Free plan and the trial start without a confirmed email, so the per-email trial rule counts addresses the person may not own, and one person can collect free use with many addresses (the trial is still once per account, per normalized email and per network; disposable domains are refused). Where the controls above say "confirmed email", that applies only when the setting is `true`; the invite-a-friend bonus always needs a confirmed email | Set `EMAIL_VERIFICATION_REQUIRED=true` if free or trial abuse appears; watch internal console → Accounts |
| Credits and billing scope | Credits never expire; no proration between plans; no invoices beyond payment receipts | Not planned for this release |
| Company features for individuals | Company features are hidden and refused for individual accounts; company sign-up is "coming soon". Existing company tenants keep them | Company onboarding (later phase) |
| Trial abuse | Controls raise the cost of repeated trials (each needs a confirmed mailbox), but a determined person with new mailboxes and networks can still claim more | Watch internal console → Overview and Accounts; revoke licences or suspend companies; trials are not card-verified (payment is only taken when a plan is bought) |
| Licence changes while offline | Expiry and revocation reach a browser at its next server request (sessions ≤ 15 min, sync every 5 min); there is no instant remote lock for a disconnected browser, but it cannot get a new session either | Short sessions; the browser locks when its session ends |
| Payments | Implemented with Razorpay but acceptance-tested only against a fake Razorpay; not yet run in Razorpay test mode with live webhooks. Missed subscription-charge webhooks are not reconciled (Reconcile covers one-time orders only). Receipts are payment receipts, not GST tax invoices. No proration when switching plans | Run the test-mode checklist in TESTING.md before live keys; watch the webhook log in internal console → Payments |
| Shared activation code | An unused code works for whoever pastes it first within 30 minutes | Don't share codes; revoke unexpected browsers in Users & Devices; admin approval of new browsers |
| Windows app (2.4) | Any program running as the same Windows user can ask the app's key store to sign, and so obtain browser codes for that PC (it could equally use the browsers themselves). The silent install of the extension on a personal (not domain/MDM-managed) PC works only for store-published copies (Chrome Web Store / Edge Add-ons; Brave uses the Chrome Web Store); with the self-hosted package, browsers ignore the policy there. Browsers show "Managed by your organization". Windows only; macOS/Linux use one browser at a time with a code. The app and installer are not code-signed in this repository, so Windows SmartScreen warns until they are | Publish to the stores and set the store IDs; sign `AgentShieldHelper.exe` and the setup with a code-signing certificate; remove unknown PCs in the portal |
| Lockout, rate-limit and challenge-replay counters (customer, staff and personal API tokens) | In memory, per process (a restart clears them; each worker counts separately) | Shared store (e.g. Redis) or a rate-limiting proxy for multi-worker deployments |
| Legacy device keys | `LEGACY_DEVICE_KEYS_ENABLED=true` re-accepts the retired organization-wide keys | Leave it off (default); use it only briefly while migrating |
| Website categories are list-based | New sites appear daily and lists are never complete; the lists only update when a new extension version is built (`node scripts/update-web-categories.js`) and installed; subdomains of never-block domains (e.g. pages hosted on Blogspot or Google storage) are not blocked by category; "Filter bypass" blocks VPN/proxy websites, not a VPN app or the browser's own encrypted DNS; Safe Search covers Google, Bing, DuckDuckGo and YouTube only; category blocking only works in browsers with the extension (incognito only if the user allows the extension there) | Rebuild and release regularly; DNS filtering (e.g. a family/security DNS) for devices and other browsers; force-install with incognito allowed on managed devices |
| Category data licence | The category lists come from the HaGeZi DNS blocklists (GPL-3.0) and are shipped as data files with attribution (`extension/rulesets/LICENSE-DATA.md`) | Have the distribution terms reviewed before store publishing |

## 6. Extension permissions

| Permission | Why |
| :--- | :--- |
| `<all_urls>` host access | Block any domain the admin chooses, the chosen website categories, and AI sites until activation; prompt checks themselves only run on supported AI sites (`shared/domains.ts: SUPPORTED_AI_HOSTS`). |
| `declarativeNetRequest` | Network-level website blocking, the built-in website-category rulesets and Safe Search rules. |
| `storage` | Cache rules and queue events (`local`), hold the short-lived session (`session`, cleared on browser exit), read managed policy (server address only). |
| `tabs` | Backup redirect of blocked sites; push rule updates to open tabs. |
| `alarms` | Renew the session and sync every 5 minutes; while the Windows app is installed but the PC is not connected yet, ask the app again every minute. |
| `nativeMessaging` (1.8.0) | Ask the AgentShield Windows app (`com.agentshield.helper`, installed by the Windows setup) for a single-use activation code, so a PC connected once connects every browser. Without the app installed, nothing happens. |

The employee identity is the activated account's email, issued by the server; the extension no longer reads the browser profile (`identity` permissions removed). `web_accessible_resources` is limited to the icons and the block page. `client-config.json` and managed policy can only set the server and dashboard addresses; they carry no credential.
