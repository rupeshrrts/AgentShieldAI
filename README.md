# AgentShield — AI Data Protection for the Browser

AgentShield stops employees from accidentally leaking passwords, API keys, customer data and confidential company information into AI tools such as ChatGPT, Claude and Gemini. A Chrome/Edge extension checks prompts and file uploads **inside the browser, before anything is sent**, and allows, monitors, warns, redacts or blocks them according to rules IT manages centrally. It also blocks risky websites and unapproved AI tools, and keeps an audit trail.

This README is the single entry point for people **and AI coding agents**. Read [For AI agents and contributors](#for-ai-agents-and-contributors) before changing code.

## Customer journey (individual accounts)

Since 2.1.0 the public product is the **Individual** account; **Company** workspaces are shown as "Coming soon" (existing company tenants keep their company features). Everything happens in one portal with one sign-in (details for the person: [USER_SETUP.md](./USER_SETUP.md)):

1. **Sign up** on the portal's sign-in page → **Create an account** → **Individual** (name optional, email, password). You are signed in at once.
2. **Confirm your email** from the emailed link (`#verify=…`). Needed before the free trial; a banner offers **Send a new link**.
3. **Start a plan** on **Account & plan**: the free 30-day trial, a monthly / 6-month / annual plan, or prepaid **credits** (pay as you go), paid in Razorpay's hosted Checkout.
4. **Download.** Add the AgentShield extension to Chrome or Edge (store link, or the zip with Load unpacked until it is published). No Windows program is needed (2.6). The optional Network Agent (`AgentShield-Agent.exe`, 2.5) is offered separately for browsers the extension cannot cover.
5. **Connect.** **Connect browser → Generate activation code** (single-use, 30 minutes) → paste it into the extension → **Connect and verify**. AI sites are now protected. Each browser connects with its own code.
6. **Manage everything in the same portal:** usage and credits, security alerts, protection rules and website controls, connected browsers, personal API tokens, profile and password.

**Free forever (2.3):** once the email is confirmed, an individual account without a live plan is on the **Free plan**: 300 prompt checks per UTC month on 1 browser (staff can change both). When they are used up, AI sites stay usable and website controls keep working, but prompt checks pause ("Protection paused") until the 1st, an upgrade or credits. When a trial or plan ends, individuals move to the Free plan instead of being locked. **Invite friends:** the Account page has an invite link (`/#ref=<code>`); when a friend signs up with it and confirms their email, both accounts get 100 bonus prompt checks (credits), for up to 10 friends.

For company workspaces (and individuals without a confirmed email): when the trial or plan ends, the plan's included monthly prompt checks or the credits run out, or the person's own monthly limit is reached, every browser of the account **locks automatically at its next request** (AI sites blocked) and **unlocks by itself** after renewal, a top-up or a higher limit, without reinstalling or a new code.

## Quick start (one PC, 10 minutes)

Prerequisites: Python 3.10+, Node.js 18+, Chrome or Edge.

**Fastest way — one command in any terminal (VS Code, Antigravity, cmd, PowerShell):**
```
npm start
```
Run it in the project folder. It installs what is missing on the first run, builds the extension and runs the backend (:8000),
public website (:5172), user dashboard (:5173) and developer console (:5175) together in that one terminal; Ctrl+C stops everything. Sign-up
confirmation links are printed in the same terminal. It always uses a local test database (`backend\local_test.db`), never Supabase.
- First time, create your developer-console login: `npm start -- --owner you@company.com`
- Start from empty test data: `npm run reset`
- **Emails are not sent locally** unless `.env` has `SMTP_HOST` and `SMTP_FROM` (plus `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`); confirmation, reset and invite links are then printed in the terminal, highlighted in yellow, and the portal says so (`GET /auth/signup-info` → `email_delivery`). `npm start` reads only the `SMTP_*` lines from `.env`; the database is still the local test file.
- The browser opens the **website (http://localhost:5172) first**; its Sign up / Log in buttons lead to the user dashboard (:5173). Add `-- --no-open` to skip opening the browser.

(VS Code users can also press Ctrl+Shift+B.) The manual steps below do the same thing by hand.

```powershell
# 1. Backend (local database; never point a dev server at production)
cd backend
python -m venv .venv
.venv\Scripts\pip install -r requirements.txt
$env:DATABASE_URL = "sqlite:///./agentshield.db"
$env:DEMO_MODE = "true"
# Optional but recommended: a fixed signing key. Without it a random key is used per process, so every
# restart (including --reload) signs everyone out and enrolled staff authenticators can no longer be read.
$env:SECRET_KEY = (.venv\Scripts\python.exe -c "import secrets; print(secrets.token_hex(32))")
.venv\Scripts\python.exe -m uvicorn app.main:app --reload --port 8000

# 2. Customer portal / dashboard (new terminal)
cd dashboard; npm install; npm run dev        # http://localhost:5173

# 3. Extension (new terminal)
cd extension; npm install; node build.js

# 4. Optional: internal admin console for AgentShieldAI staff (new terminal)
cd admin-console; npm install; npm run dev    # http://localhost:5175
```

There are **no built-in logins**. Create accounts as follows (all development only):

4. At http://localhost:5173 click **Create an account** → **Individual** (name, email, password): you are signed in at once. Without SMTP settings the confirmation link (`/#verify=…`) is printed in the backend console; open it, then claim the free trial on **Account & plan**. (Alternatively set `INITIAL_ADMIN_EMAIL` and `INITIAL_ADMIN_PASSWORD` before the first start to create a first **company** workspace and its admin with an internal licence; `DEMO_AUDITOR_PASSWORD` additionally creates a read-only `auditor@agentshield.local`, never in production.)
5. **Connect browser** (**My activation** in a company workspace) → **Generate activation code** → copy the `ASA1.…` code (single-use, 30 minutes). To try another account, sign up again with another email; to try an employee account, use the initial company workspace and invite one in **Users & Devices** (without SMTP settings the invite link is printed in the backend console).
6. `chrome://extensions` → Developer mode → **Load unpacked** → `extension/`. AI sites now show "Activation Required". Click the AgentShield icon, paste the code, **Connect and verify**.
7. Open **Guided Demo** in the dashboard and run the steps (or use http://localhost:8000/test-bench).
8. Internal console (optional): in `backend/`, with the same `DATABASE_URL` (and `SECRET_KEY`) as the server, run `.venv\Scripts\python.exe -m app.cli create-platform-owner --email you@example.com`. It prints a temporary password once. Sign in at http://localhost:5175, scan the QR code with an authenticator app, save the 10 recovery codes, then choose a new password (at least 14 characters).

## How it works

```
EMPLOYEE BROWSER                                              YOUR SERVER
┌──────────────────────────────────────────────┐             ┌───────────────────────────────┐
│ AI site                                      │             │ FastAPI (:8000)               │
│  content.ts: catches send / upload ──┐       │             │  /api/v1/policies   sync      │
│  detector.ts: findings               │       │             │  /api/v1/domains    sync      │
│  policy.ts: BLOCK>REDACT>WARN>MONITOR>ALLOW  │  HTTPS +    │  /api/v1/events     ingest    │
│  overlay.ts: dialog / reason ────────┘       │ device JWT  │  /api/v1/endpoints  heartbeat │
│ service-worker.ts: activation gate, sync, ───┼────────────►│  /api/v1/device/*   activation│
│   network blocking, heartbeat, queue         │             │  /api/v1/org/*, /me/*, /auth/*│
└──────────────────────────────────────────────┘             │        │                      │
ADMIN BROWSER: React dashboard ── HTTPS + JWT (typ=user) ───►│   PostgreSQL / Supabase (RLS) │
STAFF BROWSER: admin-console (own origin) ─ HTTPS + staff ──►│  /internal/auth/*, /internal/api/*
               JWT (typ=staff, issued only after TOTP MFA)   └───────────────────────────────┘
```

* **Prompt flow:** capture-phase listeners stop the submission → local detection → policy decision (+ employee status) → dialog → masked event to the service worker → backend (or offline queue). A confirmed prompt is approved once, for its exact text, for 5 s.
* **File flow:** the upload event is stopped → `file.upload` rule + content scan of text files → allowed uploads are re-dispatched to the page.
* **Website flow:** `declarativeNetRequest` rules block before load; `domain-blocker.ts` and `tabs.onUpdated` are backups; all use `shared/domains.ts`.
* **Activation flow:** the worker starts `LOCKED` (AI sites blocked) → the user signs in to the dashboard (or creates an account), generates a single-use code in My activation and pastes it into the popup → the browser's new key pair is registered → each 15-minute session is obtained by signing a server challenge → `AUTHORIZED`; revocation, a disabled account or an unreachable server lock it again (`background/auth-state.ts`, `api/device_auth.py`).
* **PC flow (Windows app, 2.4; retired from the extension in 2.6):** the extension (1.9.0) no longer has the `nativeMessaging` permission and never talks to the Windows app, so it needs no `.exe`. The server's `/api/v1/computer/*` endpoints remain for the optional Network Agent (`agent/`); PCs connected earlier are listed in **Connect browser** only so they can be removed.
* **Network Agent flow (optional, 2.5):** a free self-hosted local proxy (`agent/`) for PCs where the extension cannot reach everything (Firefox, other browsers, desktop AI apps). It connects the PC with a portal code through the same `/api/v1/computer` → `/api/v1/device` flow, then **opens only the AI domains** (everything else is tunnelled, never decrypted), extracts the prompt from each AI request and applies the **same detector and policy evaluator as the backend** — Block / Redact / Warn / Monitor / Allow — before the request reaches the site. It is fail-closed and holds one device slot. The extension stays the primary control; the agent is the gap-filler. See [agent/README.md](./agent/README.md).
* **Sync (2.6):** while authorized: right after sign-in, then **every minute** a cheap check of the organization's revision (`GET /api/v1/policies/revision`; every enforced dashboard change increases it), with a full download only when it changed or at least every 5 minutes, and on "Sync policies". A heartbeat follows each full sync. Open AI tabs get the new rules at once (`POLICIES_UPDATED`).
* **Enforcement follows the dashboard (2.6):** a protection rule is enforced only by an **enabled** policy row (no built-in default action), a website category only while switched on, Safe Search only while on, unapproved AI sites only while that switch is on, a website rule only while enabled. Until the synced rules contain every catalog rule, prompts and uploads are not sent (fail closed, "Protection rules loading").
* **Two web apps:** the customer portal (`dashboard/`) serves customer companies only; AgentShieldAI's own staff use the separate internal admin console (`admin-console/`) on its own origin. They use different accounts (`users` vs `staff_users`) and different token types, and neither app's tokens work on the other's APIs.

## Authentication model

| Caller | Credential | Can |
| :--- | :--- | :--- |
| Dashboard Admin / Viewer | `Authorization: Bearer <JWT>` (`typ=user`) | Admin: manage own organization. Viewer: read only |
| Employee | `Authorization: Bearer <JWT>` (`typ=user`, role `EMPLOYEE`) | Only `/auth/*` and `/api/v1/me/*`: generate activation codes, manage own browsers |
| Browser extension | `Authorization: Bearer <device session JWT>` (`typ=device`, 15 min) | Read rules/domains/keywords/settings, read its own account's status, submit events and heartbeats, sign itself out |
| AgentShield Windows app (2.4) | No session: each call carries a fresh 60-second challenge (`typ=computer_challenge`) signed with the PC's non-exportable key | Only `/api/v1/computer/browser-code`, `/status`, `/deactivate`: get single-use codes for the PC's own browsers, check or remove its own connection |
| AgentShieldAI staff (internal console) | `Authorization: Bearer <staff JWT>` (`typ=staff`, `STAFF_TOKEN_HOURS`, default 8 h), issued only after password + authenticator code | Only `/internal/*`, each route limited to one permission (table below) |

Customer roles today are `ADMIN`, `VIEWER` and `EMPLOYEE` (Phase B will add Company Owner / Security Manager, seats and departments). The former customer role `SUPERADMIN` no longer exists: at startup (and in `2026_10_internal_console.sql`) such accounts become `ADMIN` of their own company, and they no longer open any platform pages.

**Account types (2.1).** `organizations.account_type` is `INDIVIDUAL` (public sign-up; one person, who is its `ADMIN`) or `COMPANY` (every tenant created before 2.1, the initial company, and sign-ups only when `COMPANY_SIGNUP_ENABLED=true`). Company-management routes (`/api/v1/org/users`, invites, `/api/v1/org/devices`) depend on `require_company_workspace` and answer individual accounts with 403 `COMPANY_FEATURE_UNAVAILABLE`; their own browsers stay manageable under `/api/v1/me/*`.

**Token separation.** Customer dependencies (`api/deps.py`) accept only `typ=user` / `typ=device`; internal dependencies (`core/permissions.py`) accept only `typ=staff`. Customer and device tokens get 401 on `/internal/*`; staff tokens get 401 on customer APIs. The staff sign-in step tokens (`typ=staff_mfa`, 5 min; `typ=staff_mfa_setup`, 10 min) are not sessions and only work on their own MFA step.

**Staff sign-in** (`api/staff_auth.py`): `POST /internal/auth/login` (email + password) → step token, never a session → `POST /internal/auth/mfa/verify` with a 6-digit TOTP code or a recovery code → session. A staff member without an authenticator first enrols one (`/mfa/setup` returns the secret and `otpauth://` URI; the console shows a QR code and the manual key; `/mfa/enable` with a valid code returns 10 single-use recovery codes, shown once, and the session). TOTP codes cannot be replayed (last accepted step stored); secrets are Fernet-encrypted at rest (key `STAFF_MFA_KEY`, or derived from `SECRET_KEY`); recovery codes are stored only as SHA-256 digests bound to the staff account (`_recovery_hash`: digest of staff id + code; the codes are random, so this is not a password hash). 5 failed passwords lock the email for 15 min. A temporary password (bootstrap) must be changed before anything else (403 `PASSWORD_CHANGE_REQUIRED`). Sessions carry a session version, so password change, sign out everywhere, role change, disabling, MFA reset and "end sessions" end them at once. Everything is audited with `actor_type=staff`.

**Staff accounts.** The first platform owner is created with `python -m app.cli create-platform-owner --email you@company.com` (run in `backend/` with the production environment / `DATABASE_URL`); it prints a random temporary password once and refuses if an owner already exists unless `--force`. Further staff only by owner invite: a single-use 48-hour link `<ADMIN_CONSOLE_URL>/#staff-invite=ast_…` sent by email (in development without SMTP, written to the server log). The owner can change roles, disable, reset MFA and end sessions; the last active owner cannot be demoted or disabled.

**Licence exceptions.** Paid access normally comes only from a verified payment. Granting a PAID or INTERNAL plan, or extending a non-trial licence, without one is an exception: it needs `licenses.exception` (owner only) and a reason; a granted exception is stored with `payment_ref = exception:<staff email>` and audited as `platform.license_exception` (extensions are audited as `platform.license_extend` with before/after dates). Trial grants and trial extensions need `licenses.manage`. The same applies to credits (2.1): `POST /internal/api/companies/{id}/credits` with a positive amount is an owner-only exception (`licenses.exception`, reason required, audited `platform.credits_exception`); removing credits needs `licenses.manage` (audited `platform.credits_adjust`). Credit packs (`CREDITS` plans) cannot be granted as licences.

**No built-in credentials.** No default admin, no default `SECRET_KEY` (required in production; development without it uses a random key per process), no demo logins in the portal. `INITIAL_ADMIN_EMAIL` + `INITIAL_ADMIN_PASSWORD` (both needed) optionally create a first customer company and its admin; `DEMO_AUDITOR_PASSWORD` optionally creates a read-only demo account (never in production).

* **Accounts** come from self sign-up on the login page (`/auth/signup` with email + password, optional `name`, `account_type` `INDIVIDUAL` by default → 201 with a session, same shape as `/auth/login`; an already registered email gets 409; `SIGNUP_ENABLED`, `SIGNUP_ALLOWED_DOMAINS`) or, in company workspaces, from admin invites (`/api/v1/org/users/invite` → `/#invite=asi_…` → `/auth/accept-invite`). An individual sign-up creates a one-person account named after the person (or the email's local part) with the person as its `ADMIN`. `account_type: COMPANY` is refused with 403 `COMPANY_COMING_SOON` unless `COMPANY_SIGNUP_ENABLED=true` (then a company named from `company_name` or the email domain is created). `GET /auth/signup-info` reports `individual_enabled` and `company_enabled`. Sign-up signs the person in at once **and** emails a single-use confirmation link (`/#verify=asv_…`, `EMAIL_VERIFY_EXPIRE_HOURS`); `/auth/verify-email` sets `email_verified_at`, `/auth/resend-verification` sends a new link (rate-limited, same answer either way). A confirmed email is required only to claim the free trial (`api/billing.py: trial_eligibility`); sign-in, buying plans or credits, activation codes and activation do not need it. A password-reset link also marks the email verified. `PATCH /auth/me` sets the person's `display_name` (for an individual account it also renames the account).
* **Activation:** `POST /api/v1/device/activate` needs only a single-use activation token (`asa_…`, 30 min) generated by a signed-in, active account in My activation (it identifies that account) and the browser's new ECDSA P-256 public key; the extension never asks for a password. The dashboard shows the token as an activation code = `ASA1.` + base64url(JSON `{u: server URL, t: token}`) (`makeActivationCode` in `MyActivation.tsx`, `parseActivationCode` in `extension/src/shared/config.ts`).
* **Sessions:** `POST /challenge` → nonce (60 s, single use) → the browser signs it with its non-extractable private key → `POST /session` → session JWT. Every request re-checks device ACTIVE, account active, organization.
* Invite and activation tokens are stored only as SHA-256 hashes; the server stores only device public keys. The organization and employee always come from the credential.
* Managed policy / installer `client-config.json` can only set `apiUrl` and `dashboardUrl`; they grant no access. Legacy `X-Device-Key` keys are rejected unless `LEGACY_DEVICE_KEYS_ENABLED=true`.

## Browser extension

* **Permissions (1.9.0):** `storage`, `alarms`, `tabs`, `declarativeNetRequest`, host access to all sites (website controls apply everywhere; prompt checks run only on AI sites). Justifications for the store review: [STORE_SUBMISSION.md](./STORE_SUBMISSION.md).
* **Rule sync (1.9.0):** alarm `policy-refresh` every minute → `GET /api/v1/policies/revision`; when it differs from the revision of the last full sync (or 5 minutes have passed) → full `syncPolicies()`, network rules, category rulesets and a `POLICIES_UPDATED` broadcast. `shared/policy.ts`: `actionForRule` enforces only enabled rows; `policiesComplete()` must be true (every `CATALOG_RULE_IDS` present) before `content.ts` sends anything.
* **Builds:** `node build.js` (development, localhost defaults); `node ../scripts/packaging/store-packages.js --api-url … --dashboard-url …` (store packages, production addresses baked in, then checked); `node build.js --e2e` is only for `tests/e2e/rules-e2e.js` (lets the test drive the popup page from a tab) and is never packaged.
* **Storage:** `chrome.storage.local`: `activation` (server, device ID, email; no secret), `installId`, `syncState`, `policies`, `keywords`, `settings`, `domain_rules`, `blocked_domains`, `allowed_domains`, `domain_lists`, `userStatus`, `eventQueue`. `chrome.storage.session`: `deviceSession` (cleared when the browser closes). IndexedDB `agentshield-identity`: the non-extractable device key pair. The authorized state is never read from storage.
* **Supported sites:** `SUPPORTED_AI_HOSTS` in `shared/domains.ts` (also blocked while locked), selectors in `adapters/chatgpt.ts` (plus `test-bench` on localhost). When a site changes its layout, update the selectors there.
* **Plan and usage states (extension 1.5.0, with server 2.1.0):** `CREDITS_ACTIVE` (prepaid credits, popup "Pay as you go" with the prompt checks left) unlocks like a subscription; the refusal codes `USAGE_LIMIT`, `SPEND_CAP` and `NO_CREDITS` lock the browser like an expired plan but keep its identity, so it unlocks by itself after a top-up or renewal (`background/auth-state.ts`). Every event carries a random `client_event_id`, so retries and offline-queue replays are metered once.
* **Build/test:** `npm install`, `node build.js`, `npm test`, `npx tsc --noEmit`; real browser (Microsoft Edge, throwaway database, no internet): `npm run test:e2e`.

## For AI agents and contributors

### Golden rules
1. **Never run tests or a dev server against the database in `.env`** without checking it; it may be the live Supabase database. Set `DATABASE_URL` to a temporary SQLite file.
2. **Never commit or print secrets:** `.env`, activation codes (`ASA1.…`) and tokens (`asa_…`), invite and confirmation links/tokens (`asi_…`, `asv_…`), staff invite links/tokens (`ast_…`), personal API tokens (`aspt_…`), session tokens (customer, device and staff), staff temporary passwords, authenticator secrets and recovery codes, legacy device keys (`asd_…`) and enrollment codes (`ASE1.…`), passwords. Never add default credentials, default secrets or demo logins to shipped code (`test_no_hardcoded_secrets.py` fails the build).
3. **Auth:** extension-facing endpoints use `get_principal`; organization data uses `get_current_user` (operators only); own-account endpoints use `get_signed_in_user`; admin changes use `get_current_admin` and call `record_admin_action`. Internal (`/internal/api/*`) routes use `require_staff("<permission>")` with a permission from `STAFF_PERMISSIONS` (never a role check) and audit with `actor_type="staff"`; never let a customer token reach them or a staff token reach customer APIs. Never put admin credentials or a shared key in the extension, and keep it fail closed: only a server-issued session may unlock it.
4. **Tenant isolation:** take the organization from the credential and filter every query by it.
5. **Privacy:** prompt text written to the DB goes through `prepare_prompt_for_storage()`; the extension sends only `maskSecretsForAudit()` output, and only when settings allow.
6. **Keep the twins identical:** `detector.ts` ↔ `detector.py`, `shared/policy.ts` ↔ `policies/evaluator.py`. Add cases to `detection_cases.json`; both test suites must pass.
7. **New rule IDs** must be added to `core/catalog.py` (otherwise the API rejects policies for them), both detectors, and `RULE_LABELS`/`RULE_ADVICE` in `shared/policy.ts`. (The extension has no built-in rules any more: it enforces only rules synced while authorized.)
8. **No fake data or success messages** in the dashboard; every number must come from the API.
9. **Do not edit generated files:** `extension/dist/**`, `extension/src/popup/popup.js`, `dashboard/dist/**`, `admin-console/dist/**`.
10. **Schema changes:** prefer new tables; for new columns add to `_align_schema()` and a file in `backend/migrations/`; new tables get RLS automatically on PostgreSQL.

## Known limitations

Summarised from [SECURITY_ARCHITECTURE.md §5](./SECURITY_ARCHITECTURE.md#5-limitations-not-enforced): Chromium browsers only; employees can remove an extension unless it is force-installed by policy; PDF/Office/image content is not inspected; pattern-based detection can miss rephrased data; site layout changes can disable prompt checks on that site; customer accounts use email + password (no SSO/MFA; staff have TOTP MFA but no hardware-key/WebAuthn option); the staff session token is in `sessionStorage`, so an XSS in the console would expose it (the console loads no third-party scripts, only Google Fonts); the internal console has no customer analytics, support or further operations pages yet (Phases B–D); INTERNAL licences still exist for the initial company created from `INITIAL_ADMIN_*`; sign-up signs in before the email is confirmed, so someone can register an address they do not own (the trial still needs the confirmation link) until the owner takes it over with Forgot password; usage metering counts only what activated extensions report (a modified extension could under-report, and the server cannot see prompts that are never reported, but protection stops server-side when access ends); the offline event queue is capped at 500 events; the usage month is the UTC calendar month; credits never expire and there are no invoices beyond payment receipts; Company features are hidden and refused for individual accounts (existing company tenants keep them); a user with developer mode can edit a self-installed extension to skip the activation screen (the server still refuses it); lockout/rate-limit counters (customer and staff) are per-process memory; no automatic deletion of the admin audit log; the dashboard loads Google Fonts; Vite 5 dev-server advisories (dev only); payment receipts are not GST tax invoices; no proration when switching plans; reconciliation covers one-time orders only (monthly charges rely on webhooks).

### 2.4.6 — Faster start-up (slow first sign-in on the free Render plan) (2026-10-19)
* **Cause:** the live backend runs on Render's free plan, which sleeps after ~15 minutes idle; the next request (often a sign-in) waits until the container has booted and the backend's start-up has finished. The awake server answers in under a second (measured: `/health` 0.1 s, `/auth/login` 0.5 s).
* **Start-up uses far fewer database round trips** (each one crosses from Render Singapore to Supabase Tokyo): tables are created only when one is missing (`main.py`); `_align_schema` reads all columns in one query and adds only missing ones, and enables Row Level Security only on tables that lack it (it used to re-run ~25 `ALTER TABLE … ADD COLUMN` and ~35 `ENABLE ROW LEVEL SECURITY` statements on every start); catalog policies are checked with one query for all organizations instead of one per organization (`seed.py`); the retention clean-up runs in the background after the server accepts requests (it also still runs periodically on ingestion). Measured on SQLite: a restart went from 77 statements + 3 per organization to 26, independent of the number of accounts.
* **Portal:** when sign-in or sign-up takes over 5 seconds, the form says the server is starting up and may take up to a minute (`Login.tsx`).
* **Still needed for a fast first sign-in:** Render's own wake-up (~1 minute) remains on the free plan. Switch to Starter, or keep it awake with an uptime monitor on `/health` (DEPLOY_STEPS.md).

* **Fail closed:** the extension starts `LOCKED` and blocks all AI sites (network rules, page script and content-script gate) until authorized; an unreachable server, revocation or a disabled account lock it again. No built-in default rules, no offline bypass, no trusted cached flag. New popup "AgentShieldAI — Activation Required" with the three steps, the activation code box, "Connect and verify" and live connection status.
* **Server-side:** event and heartbeat employee/device IDs come from the authorized device, not the request; employee accounts cannot read organization data; rate limits on sign-in, sign-up, invites, code generation and activation; sign-up never reveals whether an email is registered; the startup step that marks pre-1.3 accounts verified never touches self-registered accounts; PBKDF2 raised to 600,000 iterations for new password hashes; all account and device actions audited.
* **Extension:** version 1.3.0; `identity` permissions removed; managed policy / `client-config.json` accept only `apiUrl` and `dashboardUrl`. Installers set the server address (`/SERVER=`) instead of embedding a code.
* **Tests:** `backend/tests/test_activation.py` (acceptance tests), extension state-machine and lock tests, `activation-roundtrip.js`.
